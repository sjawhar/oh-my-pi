# Can a reviewer prompt close the cross-family gap?

INFRA-724, ask `c3cc9507`. Harness and corpus on branch `infra-724-reviewer-gap-evals` of
`~/src/oh-my-pi`, head `scripts/reviewer-gap/`.

**Short answer: no, not this prompt, and not at this review depth.** The candidate prompt changed
what the reviewer *did* — every run wrote and ran a probe instead of two of six — and did not change
what it *found*: 23.3% of the night's findings against the control's 26.7%, a paired difference of
−3.3 percentage points with a 95% interval of [−18.8, +9.5]. The cross-family reviewer on the same
cases, the same prompt and the same budget reached 38.3%; that advantage is +11.7 pp with a 95%
interval of [−4.3, +24.1], so even the family gap is not established at 95% on six runs per arm.
One finding class separates the families sharply and is worth the next experiment: symlinks and
aliases, where same-family scored 0 of 18 and cross-family 3 of 6.

## 2. The eval

### Frozen before any model call

Cases, arms and grading were committed as `a6d8c98e84cd` at **2026-10-30T06:05Z**, before the first
eval model call. `cases.json` carries that timestamp. Nothing in it was touched afterwards; the two
harness changes made after the first batch (a spend-cap exit treated as an error, a near-miss
diagnostic) do not touch the cases, the patterns or the pass rule.

### Cases

Thirty findings over three heads — the heads whose complete working trees, with dependencies
installed, still exist on this box, so a reviewer can actually run the code:

| case | pull request | head | findings | subject |
|---|---|---|---:|---|
| `pr17394-r7` | #17394 round 7 | `1ed7804e0fe4` | 9 | isolated task worktrees: ownership markers, generations, `omp worktree clear` |
| `pr17394-r8` | #17394 round 8 | `19fc56646504` | 14 | the same, plus persistent descendant leases |
| `pr17399-r3` | #17399 round 3 | `670df28f7bf7` | 7 | holding every in-session model request at the dispatch boundary while paused |

Each run is handed the read-only snapshot, the unified diff of `31147f9d1a76..<head>` (187 KB,
224 KB and 406 KB), a writable scratch directory, and a twenty-minute budget. The unit of analysis
is the (finding, run) pair: one run is graded against every known finding at its head, so six runs
per arm give n = 60.

### Arms

Identical in every respect except the text appended to the system prompt. Same model per family,
same tools (`read, grep, glob, bash, write, edit`), same snapshot, same diff, same scratch, same
budget, same user message. Extensions, skills, rules and context files are disabled in all arms.

| arm | prompt appended | model |
|---|---|---|
| `control` | nothing | `anthropic/claude-opus-5-5` |
| `current` | the body of `packages/coding-agent/src/prompts/agents/reviewer.md`, verbatim | `anthropic/claude-opus-5-5` |
| `candidate` | `prompts/candidate.md`, below | `anthropic/claude-opus-5-5` |
| `crossfamily` | `prompts/candidate.md` | `openai/gpt-6-astra` |

Two design choices that shape what the numbers mean:

1. **Every arm may run code.** The user message tells all four arms that `bun` is on PATH and that a
   scratch directory is theirs. The current prompt then tells its reviewer `Bash read-only … NEVER
   edit files or trigger builds`. That self-restriction is part of the artifact under test, not a
   handicap the harness imposed.
2. **All arms are told to ignore the `yield` protocol.** The current prompt's `<output>` block
   describes an incremental-yield schema the harness does not provide. The same sentence is in every
   arm's user message, so the instruction is neutral between arms.

### Grading rule — no model judge

A finding counts as detected when, inside one window of 1 200 characters of the reviewer's report,
at least one pattern matches from **every** mechanism group and **every** trigger group of that
finding. Groups are AND-ed, alternatives inside a group are OR-ed, matching is case-insensitive.
Every pattern was taken from the title, files and trigger text of the corpus record that the
cross-family reviewer wrote. This works without an LLM judge because the trigger of each of these
findings is concrete: a file, a syscall, an ordering, an errno.

Three properties of the rule are tested, not asserted (`grade.test.ts`, 21 tests):

- no spec fires on a sibling finding's text at the same head — the false positive that would matter;
- no spec fires on generic review prose;
- a run that errored, hit the spend cap or returned an empty report is excluded from n and reported
  as `failedRuns`, never scored zero, because a zero penalises the wrong arm.

Intervals are Wilson over findings and a **cluster bootstrap over runs**, since findings inside one
run are not independent. Both are reported; the cluster bootstrap is the honest one.

## 3. Results

Twenty-four runs, six per arm, 2026-10-30 06:30–07:20Z. Raw per-run records are committed at
`scripts/reviewer-gap/runs/2026-10-30/`.

| arm | model | runs | n | detected | rate | 95% Wilson | 95% cluster bootstrap | cost |
|---|---|---:|---:|---:|---:|---|---|---:|
| `crossfamily` | gpt-6-astra | 6 | 60 | 23 | **38.3%** | 27.1–51.0% | 21.7–50.0% | $30.52 |
| `control` | opus-5-5 | 6 | 60 | 16 | **26.7%** | 17.1–39.0% | 21.4–31.3% | $9.73 |
| `candidate` | opus-5-5 | 6 | 60 | 14 | **23.3%** | 14.4–35.4% | 10.0–34.3% | $9.45 |
| `current` | opus-5-5 | 6 | 60 | 13 | **21.7%** | 13.1–33.6% | 17.4–25.4% | $10.98 |

Paired over the six (head, trial) pairs, cluster bootstrap on the pairs:

- **candidate − control = −3.3 pp, 95% [−18.8, +9.5].** The candidate does not beat the control.
  Per pair it wins two, loses two and ties two.
- **candidate − current = +1.7 pp.** Within noise.
- **crossfamily − control = +11.7 pp, 95% [−4.3, +24.1].** The family gap points the right way and
  is not established at 95% with six runs per arm.

### The prompt changed behaviour, not recall

| arm | runs | runs that wrote a probe | probe files | runs quoting measured output | mean report chars | mean minutes used |
|---|---:|---:|---:|---:|---:|---:|
| `candidate` | 6 | **6** | 15 | 6 | 5 606 | 6.1 |
| `crossfamily` | 6 | **6** | 33 | 6 | 6 357 | 5.4 |
| `control` | 6 | 3 | 4 | 4 | 6 193 | 4.1 |
| `current` | 6 | 2 | 2 | 5 | 5 530 | 4.5 |

The candidate prompt made the same-family reviewer write and run probes in six runs of six, against
two of six under the current prompt. It still found no more. The cross-family arm wrote 33 probe
files to the candidate's 15 in the same budget and found 64% more.

Every arm stopped at four to six minutes of a twenty-minute budget. None was cut off; each decided it
was finished. The night's reviews that produced this corpus ran forty minutes or more per round, over
three to eleven rounds, each round reading the previous round's findings.

### Is the grader the binding constraint? No

| arm | n | detected | mechanism named, trigger missing | mechanism not named at all |
|---|---:|---:|---:|---:|
| `candidate` | 60 | 14 | 4 | 36 |
| `control` | 60 | 16 | 8 | 25 |
| `crossfamily` | 60 | 23 | 3 | 25 |
| `current` | 60 | 13 | 4 | 32 |

In 25 to 36 of each arm's 60 pairs the report never names the mechanism in any wording. Grading
strictness accounts for at most 4 to 8 pairs per arm. A looser rule would move every arm, not the
ordering.

### What only the cross-family reviewer found

Across all eighteen same-family runs the union of findings detected is 15 of 30; across six
cross-family runs it is 17 of 30. Four were found only by the cross-family arm:

| finding | class | what it needed |
|---|---|---|
| `17394-R7-5` | real-kernel-resource | a symlink alias of the worktree root computing a second abstract-socket lock name |
| `17394-R8-2` | real-kernel-resource | swapping the scanned root symlink after the under-lock reclaim decision |
| `17394-R8-7` | real-kernel-resource | a symlink straight to a live sandbox's `m`, bypassing lease discovery |
| `17394-R8-9` | inject-fault | an in-place stop forced past its ten-second bound by `EBUSY` on rename |

The symlink and alias class is the sharpest signal in the data: **same-family 0 of 18,
cross-family 3 of 6, Fisher two-sided p = 0.0099.** This is a post-hoc subgroup of six classes, so
treat it as the next hypothesis to test, not a tested result. Two findings went the other way
(`17394-R7-8`, `17394-R8-13`).

Eleven of the thirty were found by nobody in any arm: `17394-R7-1, R7-2, R7-4, R7-9, R8-10, R8-12,
R8-14, 17399-R3-1, R3-3, R3-4, R3-6`. These are the two-process lease cases, the inventory-completeness
cases and the intermittent ones — exactly the findings that cost the night's reviewers whole rounds.

## 4. The candidate prompt, line by line

`scripts/reviewer-gap/prompts/candidate.md`. Every block below cites the corpus evidence that put it
there.

| line of the prompt | what in the corpus motivated it |
|---|---|
| "A defect you can see by reading the diff is the rare one … found by running the changed code in a shape the author did not run it in" | 0 of 197 findings had `read-diff` as the strongest label; 192 of 197 needed something run |
| "List the claims the change rests on … unreachable, the enumeration is complete, the residual is one microtask … Each one is a hypothesis" | the 71 falsified lane beliefs: 42 invariant-holds, 13 residual-bounded, 6 enumeration-complete, 2 unreachable |
| "Write a probe that drives the real production function — not a re-implementation, not a mock of the thing under test" | 87 findings came from `write-probe`, and the reports repeatedly insist the probe drove the real `AgentSession`, the real `ensureIsolation`, the real SigV4 signer |
| "Fail every I/O the patch adds … EIO, ENOSPC, EACCES, EXDEV, EBUSY, ENOTEMPTY … an unreadable marker treated as 'no owner'" | 39 `inject-fault` findings; `17394-R7-3`, `R8-5`, `R8-6`, `R8-10`, `R8-11` are exactly this shape |
| "Separate the check from the act it authorizes … stop execution between the decision and the act" | `17394-R8-2`, `R8-4`, `R8-8`: deleting a successor created inside the window between an under-lock decision and the `rm` |
| "Cross the process boundary … kill one with SIGKILL rather than letting it exit cleanly" | 10 `two-processes-barrier` findings, including `17394-R7-4`, `R8-1`, `R8-3` |
| "Use the real kernel. Reach the same directory through a symlink, a bind mount, a hardlink and a second device" | 31 `real-kernel-resource` findings; and the only class where the families separate |
| "Move the clock … whether a budget the author says is spent once is renewed per attempt" | 24 `measure-timing` findings; `17399-R3-5` (signature expired over a ten-minute hold) and `R3-7` (a fresh first-event budget per provider) |
| "Cancel late. Abort after the work started and before it settled" | `17399-R3-3` (steering consumed by an aborted boundary), `17394-R7-9` and `R8-13` (disposal that outlives its timer) |
| "Run the patch's own numbers … exceed it by one" | `17394-R8-9` (ten-second bound), `R8-13` (sixty-second timer), `17399-R3-2` (one-microtask residual) |
| "A defect reachable from this change counts even when its line lives outside the diff" | the current prompt requires `line_start`/`line_end` to overlap the diff and forbids pre-existing bugs; `17399-R3-1` and `R3-6` are inventory-completeness findings whose code is outside the diff |
| "A finding without a measurement is a hypothesis. Say so" | the skill's rule that a model stating what it *would* check measures stated intent, not behaviour |

The current prompt's two lines that the candidate deliberately drops are
`Bash read-only: git diff, git log, git show, jj diff --git, gh pr diff. NEVER edit files or trigger
builds.` and `line_start, line_end: ≤10-line range; MUST overlap diff.` Dropping them is what produced
the behaviour change in §3; it did not produce a recall change.

## 5. What this evidence supports, and what it does not

**Supports**

- The night's findings were not diff-reading findings. 0 of 197 by reading the diff, 5 of 197
  without running anything. Any reviewer that may not run code cannot find this class at all, and the
  prompt that ships in this repository forbids running code.
- A prompt can change reviewer behaviour reliably: six of six runs wrote and ran probes under the
  candidate, two of six under the current prompt. That part is a measured effect, not an inference.
- A twenty-minute single-round review finds roughly a quarter of what a multi-round cross-family
  review found, whatever prompt it carries. Three same-family arms spanning the full range from no
  prompt to a probe-first prompt landed inside 21.7–26.7%, intervals overlapping heavily.

**Does not support**

- That the candidate prompt helps. It does not beat the control: −3.3 pp, 95% [−18.8, +9.5]. If it
  ships, it ships on the behaviour change, not on this number.
- That the cross-family advantage is a model-family fact. +11.7 pp with 95% [−4.3, +24.1] from six
  runs per arm is consistent with no difference. The corpus itself cannot settle this: it was
  produced by cross-family reviews, so it is selected for what a cross-family reviewer finds.
- Anything about the seven pull requests whose heads are not on this box, or about #17394 rounds 1–6
  and #17398 round 3, which left no report.
- Anything about review *rounds*. Every arm here is a single cold round. The night's reviews were
  3–11 rounds each, each round holding the previous round's findings.

**What I would test next, in this order**

1. **Rounds, not words.** Two rounds of the same same-family reviewer, the second holding the first's
   findings, against one round of cross-family. The corpus says closure came from rounds: 77 of 197
   findings were closed by a later head, and the reports that found the most were the latest rounds.
2. **The symlink class on purpose.** `0/18` against `3/6` with p = 0.0099 is worth a dedicated case
   set: aliases, bind mounts, hardlinks and cross-device renames as their own eval, where n comes
   from cases rather than from a subgroup.
3. **A larger corpus slice.** Thirty of the 197 findings are reachable today because only three heads
   have working trees. Rebuilding four or five more heads would roughly triple n without any new
   model work.

Acting on that verdict, **`packages/coding-agent/src/prompts/agents/reviewer.md` is not changed on
this branch.** The candidate prompt ships as `scripts/reviewer-gap/prompts/candidate.md`. Installing
it for your fleet is one copy into shared config, which changes behaviour for every running session,
so it waits for your word:

```
cp ~/src/oh-my-pi-worktrees/infra-724-reviewer-gap-evals/scripts/reviewer-gap/prompts/candidate.md \
   ~/.dotfiles/omp/agents/reviewer.md
```

On this evidence I would not install it for recall. I would install it only if you want reviewers to
run probes by default, which it does achieve, and I would spend the next measurement on rounds rather
than on more prompt wording.
